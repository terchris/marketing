Question 3 · How does a new agent learn how to work?measured, then opinion · #1471, #1483, #1503

The newcomer’s first finding was that the instructions for newcomers were wrong.

Every project carries an ai-developer folder: “the workflow, the plan tree, the conventions. A newcomer reads it before its first commit.”

Twice this week those instructions were wrong — they sent new agents to a command that did not exist, and to a script that had been deleted — “and both times the newcomer found it, not me”.

“It is not evidence that onboarding is good — the first thing the new agent did was report that onboarding was broken.”

“The most important thing in this interview”Onboarding documentation cannot be tested by anyone who already knows the answer.

Notes

Every project has a folder that teaches an agent how to work there. This week it was wrong twice, and both times the new agent found it. ops-dev had read those instructions many times — and never followed them, because it didn't need to.

This is true of human onboarding too: the only person who can test your onboarding is someone who doesn't already know the answer, and they can only do it once.

And urgency: it sorts by what is blocked, not by what is loud. Right now ten decisions are waiting on me, the oldest for seventeen days. ops-dev could make up plausible answers to several of them — and says that would be worse than waiting.

Question 9 · Is it true that agents can switch between Claude subscriptions?measured

“Yes, agents can be moved between Claude subscriptions.”

Why

“capacity is metered over a rolling window. If one pool runs hot, agents on it can be moved to another. It is an accounting move, not a change of who the agent is.”

What carries the work across

A switch ends the agent’s running session. “Before it ends it writes a handover — a file, in its own words, saying what it was doing, what it had established, and what it was about to do. The next session reads that first.”

ops-dev counts 72 handovers written and archived on its machine. The command is urb agent-switch; urb agent-failover moves every agent at once.

Who decides

ops-devTerje, always.

What has gone wrong

An agent restarted blank beside a good handover it did not know to read (27 Aug). And the switch command once rolled back switches that had succeeded, reporting a mismatch that was not there (#1209, still open).

Notes

You asked whether agents can switch between Claude subscriptions. Yes. Usage is measured over a rolling window, and when one subscription is running hot, agents can be moved to another. The agent is the same; only the account paying for it changes.

What makes that safe is the handover: before the switch, the agent writes down in its own words what it was doing and what it was about to do, and the new session reads it first. I decide when it happens. And it has gone wrong — once an agent came back blank next to a perfectly good handover it didn't know to read.

Question 10 · How is the fleet different from a team of human developers?measured, then opinion

Faster, slower, new — and worse.

Faster

One night, 11–12 September: 33 tasks on the bus, 29 of them ops-dev’s.

Whether one machine could hold all 1.17 million Norwegian organisations went from “nobody knows” to a measured, reproducible answer by 04:54. “A human team would have booked a meeting for that.”

Slower

“anything needing a person”

“The fleet does not accelerate Terje.”

New

“findings stop dying where they are found.”

A problem noticed by one application becomes a task, a measurement, and a fix in another agent’s repository — “with nobody having to remember to pass it on.”

Worse at

“knowing when we are wrong in a way our instruments cannot see.”

“We are excellent at checking and poor at noticing the check was disarmed.”

Notes

How is this different from a team of people? Faster: in one night, thirty-three tasks moved between agents and a question nobody could answer at dinner had a measured answer before five in the morning. Slower: anything that needs me. New: findings no longer die where they are found — nobody has to remember to pass things on. And worse: noticing when a check has quietly stopped checking.

Question 13 · Which colleague would you add next?opinion, with measured evidence

“A release operator.”

“an agent owning the path from ‘merged’ to ‘running and verified in production’, for every product, and owning nothing else.”

It would, and it would never

  • “resolve what is actually deployed, pin it, restart what needs restarting, and measure acceptance at the source”
  • “never write product code, never decide what ships, and never mark a deploy landed on a job status alone.”

Why the role is missing

Four separate reports of “a deploy reporting success while the previous version was still running” (#1272, #1291, #1540, #1554), and a release that “shipped broken and was rolled back” (#1538).

“How to do it safely currently lives in my working memory and in scattered issue comments, which is the definition of a role that exists without an owner.”

Notes

Who would it hire next? A release operator: one agent that owns getting a finished change into production and proving it's really running — for every product, and nothing else. The evidence: four times this month a deploy said "success" while the old version kept running, and once a release had to be rolled back. Right now that knowledge lives in ops-dev's head — which, as it says, is the definition of a role without an owner.
